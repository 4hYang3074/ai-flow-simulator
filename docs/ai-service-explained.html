以 AI Flow Simulator 为例

一个 AI 服务，是怎么跑起来的

你在聊天框里打一句话，几秒后收到回答。中间其实经过了十几个步骤，而真正“思考”的模型只占其中一步。这份报告用我们自己做的模拟器，把这些步骤一个一个拆开讲。

0

先说结论

  • ①

    模型只是一个零件。一个 AI 服务 = 模型 + 包在它外面的一大套程序。这套程序在行内叫 harness，用户感受到的“聪明”和“靠谱”，大部分来自它。

  • ②

    模型没有记忆。它每次都是一张白纸，只看得到这一次交给它的文字。所以“记得你上一句说了什么”，是 harness 把对话找出来、重新塞给模型的结果。

  • ③

    规则决定边界。什么时候不用调用模型、什么叫“指前文”、找不到时怎么办，都是事先写好的规则。最重要的一条是：记忆层也判断不了的时候，直接问用户，绝不靠猜。

1

模型能做什么、不能做什么

模拟器用的模型是 Qwen3 4B，在你自己的电脑上通过 Ollama 运行。“4B”指它有 40 亿个参数，在大模型里算很小的一类。它的工作方式可以简单理解为：读进一串文字，然后一次预测一个 token（大约一个字或半个词），接着往下写，直到写完。

模型能做的模型做不到的
理解和续写文字：回答问题、写东西、翻译、解释记得上一次调用说过什么（每次都从零开始）
按格式输出，比如只输出一段 JSON保证输出一定正确：会编造，也会把格式写坏
根据给它的材料作答知道材料以外的新信息：它不能上网，不知道今天的天气
判断“这句话在说什么”可靠地判断“我手上的信息够不够”：小模型这一点尤其弱

关键概念：prompt 就是模型的全部世界。每次调用模型，交给它的是一个消息列表（system 指令、之前的对话、这次的问题）。模型看到的就只有这些。列表里没有的东西，对它来说就不存在。在模拟器里，打开「完整流程 → 上下文组装 → 完整 Prompt」，就能看到每一轮模型真正读到的全部内容。

2

Harness：包在模型外面的那一层

Harness 原意是马具。马很有力，但没有马具就拉不了车，也不会往你想去的方向走。模型也一样：它很会写字，但谁来决定给它看什么、它写坏了怎么办、敏感信息能不能给它看？这些都由 harness 负责。

设计 harness 时，要事先想清楚并写成规则的问题，大致有这几类：

  • 给模型看什么：带几轮旧对话？哪些记忆？按什么顺序摆？
  • 什么时候不用模型：“你好”“谢谢”这种话，用模板回答就行，又快又省钱。
  • 不能给模型看什么：手机号、邮箱这类个人信息，要先换掉。
  • 模型出错怎么办：回答是空的、格式写坏了、引用了不存在的东西，怎么兜底？
  • 信息不够怎么办：这是最容易被忽略、也最重要的一条，第 6 节专门讲。
3

一句话走过的完整路线

下面是模拟器里一轮请求按顺序经过的步骤。每一步都对应模拟器右边「完整流程」里的一行，点开就能看到它真实的输入和输出。不是每一轮都会走完所有步骤：路由会决定走哪条路线。

  1. 01

    接收与校验

    Receive规则

    消息是不是空的、有没有超过 2000 字、上一条是不是还在处理。

  2. 02

    隐私脱敏

    Redact规则

    手机号变成 [PHONE_1]、邮箱变成 [EMAIL_1]。之后的每一步、包括存进数据库的，都是占位符；只有最后显示给你的回答会换回真实的值。

  3. 03

    意图路由

    Intent Routing规则模型兜底

    判断这句话属于哪一类：闲聊、普通提问、引用前文、纠正上一轮。先用规则判断，规则判断不了的短句（“为什么？”）再问模型。

  4. 04

    快速通道

    Fast Path规则

    闲聊直接用模板回答，0 次模型调用，几毫秒就完成。

  5. 05

    纠正 / 引用

    Correction / Reference规则

    “不对，我是说……”就把上一轮找出来；“第二个”就去最近的回答列表里找第二项。

  6. 06

    记忆提取

    Memory Recallharness

    取出最近 3 轮对话、长期记忆本里的事实，再用相似度检索找回更早的相关对话。

  7. 07

    上下文检查

    Context Check模型规则核对

    手上的信息够不够理解这句话？3 轮不够就扩到 5 轮，5 轮还不够就反问用户。

  8. 08

    上下文组装

    Context Assemblyharness

    把系统指令、编号材料 [M1]、最近对话、新问题拼成最终的 prompt。

  9. 09

    证据快照

    Evidence Snapshotharness

    记下这次到底给了模型哪些材料，并给整个 prompt 算一个指纹，事后可以对账。

  10. 10

    生成

    Generation模型

    模型一个 token 一个 token 地写，每写出一点就立刻送到聊天框（streaming）。这是整条路线里唯一“写回答”的一步。

  11. 11

    输出校验

    Validation规则

    回答是空的就去掉历史重问一次；检查引用的编号是不是真的给过模型；把占位符换回原值。

  12. 12

    保存

    Persistharness

    这一问一答存进 SQLite，再算一个 embedding，以后才能靠相似度找回来。

  13. 13

    长期记忆

    Long-term Memory模型规则核对

    让模型挑出值得长期记住的事实（名字、喜好、过敏），每条必须原文引用你的话，否则丢掉。

数一数：13 步里只有 3 步主要靠模型，其余都是 harness 写好的程序和规则。

4

规则：先规则，再模型

很多人以为 AI 服务就是“把问题丢给模型”。实际上，成熟的系统几乎都是规则在前，模型兜底。原因很实际：

规则模型
速度不到 1 毫秒零点几秒到几秒
成本免费每次调用都要算力（云端就是钱）
可预测同样的输入永远同样的结果同一句话问两次，可能判断不同
可测试能写自动测试逐条验证只能抽样观察
灵活只认得写进去的说法能理解各种说法

所以分工是：规则处理清楚的情况，模型处理模糊的情况，规则再检查模型的结果。模拟器里的几条规则：

规则内容为什么这样定
闲聊模板“你好 / 谢谢 / 再见 / 好的”直接回模板不值得为这种话调用一次模型
指代词“它 / 这个 / 那个”只有出现在第一句才算指前文；“刚才 / 之前 / 你说的”在哪都算“我的猫叫小白，它三岁了”里的“它”是小白，不是在指前文
相似度阈值相似度 ≥ 0.45 才把旧对话找回来实测：相关的对话 0.49–0.62，不相关的最高 0.42
事实校验长期记忆的事实必须原文引用你的话；来自问句的一律不要实测模型会从“我的猫叫什么？”里提取出“猫的名字：未知”
失败时模型输出格式错误，一律按“不确定”处理宁可多问一句，也不能拿坏掉的结果继续往下走

规则要“看得见”。模拟器里每条规则命中时都会显示出来：「意图路由」写着命中了哪条规则、哪几个字；规则判断不了时，会标明“模型判定”。这样出错时才知道是规则的问题还是模型的问题。

5

记忆：给没有记忆的模型补上记忆

因为模型每次都是白纸，“记忆”必须由 harness 来做：把对话存起来，下一次再挑出相关的部分放回 prompt。问题在于不能全部放进去：prompt 越长越慢，小模型能读的长度也有限，太多无关内容还会干扰它。所以模拟器把记忆分成三层：

3 轮

短期记忆

最近 3 轮问答原样带上。大多数追问（“那它呢？”）都指向刚说过的话。必要时扩到 5 轮，见第 6 节。

事实

长期记忆本

“名字：阿明”“猫的名字：小白”“过敏：花生”。每轮都带给模型。每条都附原文引用，新说法会取代旧的（第 2 版）。

≥ 0.45

相似度检索

更早的对话不全部带上，而是用 embedding 把每段对话变成一串数字，和新问题比相似度，够像才找回来。

真实例子（模拟器实测）：

我叫阿明，我的猫叫小白，它三岁了
长期记忆：记下「名字：阿明」「猫的名字：小白」「猫的年龄：三岁」，每条都对上了原文
推荐两个适合新手的数据库 → 明天要下雨吗？ → 我最喜欢吃披萨 …（聊了几轮别的）
我的猫叫什么名字？
第一句已经不在最近 3 轮里 → 相似度检索把它找回来（相似度 0.643 ≥ 0.45）
你的猫叫小白。

在模拟器里：左上角「📒 记忆本」显示长期事实，新事实会从你的话里飘进去；「记忆 Memory」按钮能看到哪些对话是“短期”，哪些只能“检索”。

6

判断不了就问，绝不靠猜

记忆层把材料找齐之后，还要回答一个问题：这些信息够不够理解用户这句话？比如用户说“那两个里面哪个更好？”，系统必须知道“那两个”是什么。这时有一条必须遵守的规则：

第一步

用最近 3 轮判断

大部分时候够了，直接回答。

第二步

不够，扩到 5 轮

多看两轮再判断。够了就带着 5 轮去回答。

第三步

还不够，直接问

“我不太确定『那两个』指的是什么，能说得具体一点吗？”不调用回答模型。

为什么宁可问也不猜？猜错的代价比多问一句大得多：用户会收到一个看起来很自信、但答非所问的回答，而且很难发现它是错的。问一句只多花几秒。

怎么判断“够不够”

最直接的做法是问模型“够不够？”，但实测 4B 小模型答这个问题很不可靠：完整的问题它说不够，材料就在眼前它也说不够。所以改成和长期记忆一样的思路，让模型做它擅长的事，让程序做核对：

  • 模型只负责指出这句话里哪些词在指前文（“那两个”），并原文引用它指的内容（“Rust 还是 Go”）。
  • 程序核对引用是不是真的出现在前文里（忽略标点；太短的引用如“为什么”不算数）。
  • 没有指前文的词，或者每个都对得上：够了。有任何一个对不上：不够。

有几种情况根本不用检查，由规则直接放行：第一句话、完整的新问题（“什么是向量数据库？”）、已经在列表里找到的“第二个”、纠正上一轮。

真实例子（示例剧本「上下文不够时」）：

我在考虑学 Rust 还是 Go
推荐一本适合新手的 Python 书
明天要下雨吗？
今晚吃什么好？
那两个里面哪个更适合写网页后端？
最近 3 轮里找不到「那两个」→ 扩到 5 轮 → 找到「Rust 还是 Go」，引用核对通过
对比 Go 和 Rust 写网页后端……（按 Rust 和 Go 回答）
它的价格大概多少？
如果 5 轮里都对不上「它」→ 改为反问，不调用回答模型
我不太确定「它」指的是什么。我看了最近 5 轮对话还是没法确定，能说得具体一点吗？

规则的极限也要说清楚。程序能核对“引用的话确实在前文里”，但不能保证模型引用的就是对的那一段。所以小模型有时会判得偏严、多问一句。这是可以接受的方向：多问一句的代价，远小于自信地答错。

7

检查回答：模型也会出错

模型写完不等于结束。harness 会再检查一遍，下面每一条都是模拟器测试时真实遇到过的问题：

问题处理方式
回答是空的去掉历史，只带问题重问一次；还是空就报错
引用写坏了模型把 [M1] 写成 [刘1]，或在行尾编出 [猫的信息]：检测出来并从回答里去掉
引用了没给过的编号记为无效引用，在「输出校验」里显示
假事实从问句里提取的事实、值为“未知”的事实，一律不存进记忆本
占位符回答里的 [PHONE_1] 换回真实号码再显示；存进数据库的仍是占位符

还有一个细节：streaming 时看到的字只是预览，最后的 final 才是正式答案。校验去掉坏标签、换回占位符之后，聊天框里的文字会被正式版本替换。这也是真实系统的做法。

8

用模拟器亲手验证

每个概念都能在模拟器里看到。建议按这个顺序试：

想看的概念怎么做看哪里
模型没有记忆随便问两句「上下文组装 → 完整 Prompt」：之前的对话是被重新塞进去的
记忆三层「示例 Demo → 记忆是怎么工作的」记忆本、「记忆提取」的相似度分数条
判断不了就问「示例 Demo → 上下文不够时」「上下文检查」：试了几轮、引用了什么、✓ 还是 ✗
规则 vs 模型「示例 Demo → 五条路线巡礼」「意图路由」：规则判定还是模型判定
隐私保护「示例 Demo → 隐私脱敏」「隐私脱敏」和「输出校验」：号码被换掉又换回来
每一步的细节打开「单步」，自己问一句中间的卡片会在每一步停下来

右边显示的耗时都是真实值。很多步骤不到 1 毫秒，所以中间的卡片是放慢的回放；左边聊天框的文字永远是模型一写出来就显示。

9

真正上线的系统还会多做什么

模拟器是简化版，流程是真实的，但省掉了上线必需的一些部分：

  • 身份和权限：谁能用、能看到谁的数据、每人每分钟能问几次。
  • 缓存和后台任务：把最近的对话放进 Redis 加速；长期记忆的提取放到后台慢慢做，而且要用户同意。
  • 更强的隐私保护：用专门的工具识别个人信息，而不是几条格式规则；追踪哪些数据能发给云端模型。
  • 工具调用：让模型去查天气、搜资料、算数，再根据结果回答（模拟器里没做）。
  • 监控和评估：记录每一次调用的耗时和花费，定期抽样检查回答质量。
  • 更大的模型：云端模型比 4B 强得多，但规则、记忆、检查这一整套 harness 依然需要。模型越强，harness 要防的问题会变，但不会消失。
10

术语表

Model 模型
读文字、写文字的那个部分。本身没有记忆。
Harness
包在模型外面、决定给它看什么和怎么处理它的结果的整套程序。
Prompt
每次交给模型的完整消息列表，也是模型能看到的全部内容。
Token
模型读写的最小单位，大约一个汉字或半个英文单词。
Streaming
模型每写出一点就立刻送出去，所以文字是一点点出现的。
Embedding
把一段文字变成一串数字，意思越接近，数字越接近，用来算相似度。
Context window
这里指一次带给模型的对话轮数：3 轮，必要时 5 轮。
Routing 路由
判断一句话该走哪条处理路线。
Redaction 脱敏
把个人信息换成占位符再交给模型。
Fail-closed
出问题时选择安全的一边：不确定就不做、就问，而不是继续往下猜。

本报告以 AI Flow Simulator 为示意。文中的数字（相似度、耗时、例子里的对话）来自在本机用 Qwen3 4B 实测的结果；小模型每次的判断会有差异。
